## 2. Matriz de Compatibilidad MySQL → PostgreSQL

### Sintaxis de funciones

| MySQL | PostgreSQL | Ubicación | Acción |
|-------|-----------|-----------|--------|
| `DATE_FORMAT(col, '%Y-%u')` | `TO_CHAR(col, 'IYYY-IW')` | DashboardQueryService:259 | Agregar branch `pgsql` en getDateExpression() |
| `DATE_FORMAT(col, '%Y-%m')` | `TO_CHAR(col, 'YYYY-MM')` | DashboardQueryService:260 | Agregar branch `pgsql` en getDateExpression() |
| `COALESCE(...)` | `COALESCE(...)` | DashboardQueryService, CalculateClosing | Compatible (ANSI SQL) |
| `CASE WHEN ... END` | `CASE WHEN ... END` | DashboardQueryService | Compatible (ANSI SQL) |
| `COUNT(*)`, `SUM(...)`, `ABS(...)` | Mismo | DashboardQueryService, OperationController | Compatible (ANSI SQL) |

### Semántica de base de datos

| Aspecto | MySQL/MariaDB | PostgreSQL | Impacto |
|---------|--------------|-----------|---------|
| Case sensitivity en strings | Depende de collation (insensible por defecto con utf8mb4_general_ci) | Sensible por defecto | MEDIUM — `WHERE name = 'valor'` es case-sensitive en PG; verificar búsquedas de login |
| NULL en unique constraints | Múltiples NULL permitidos | Múltiples NULL permitidos | Compatible |
| FK restrictOnDelete | RESTRICT | RESTRICT | Compatible |
| Transacciones | InnoDB: supported | Full ACID | Compatible |
| `lockForUpdate()` | `SELECT ... FOR UPDATE` | `SELECT ... FOR UPDATE` | Compatible |
| Auto-increment insert explícito | `INSERT ... VALUES (id, ...)` respeta el valor | `INSERT ... VALUES (id, ...)` respeta pero no avanza la secuencia | MEDIUM — sincronizar secuencias con `setval()` después de inserts explícitos |
| Error codes deadlock | 1213 | 40P01 | AuthTransactionRunner debe actualizar isTransientError() |
| Error codes lock timeout | 1205 | 55P03 | AuthTransactionRunner debe actualizar isTransientError() |
| `ORDER BY` con NULL | NULLs primero | NULLs último por defecto | LOW — agregar `NULLS FIRST`/`NULLS LAST` si es necesario |
| `boolean` default | `default 0` / `default 1` | `default false` / `default true` | LOW — Laravel `boolean()->default(true)` es compatible |

### Construcciones no encontradas (sin acción requerida)

- ENUM, SET, MEDIUMINT, TINYINT (fuera de operation_types), GENERATED COLUMNS
- ON UPDATE CURRENT_TIMESTAMP, AUTO_INCREMENT explícito
- Engine InnoDB, charset/collation en migraciones
- IFNULL, NULLIF, GROUP_CONCAT, FIND_IN_SET, JSON_EXTRACT/UNQUOTE/CONTAINS
- UNIX_TIMESTAMP, FROM_UNIXTIME, WEEK/YEAR/MONTH/DAY en raw SQL
- ON DUPLICATE KEY UPDATE, INSERT IGNORE, REPLACE INTO, LAST_INSERT_ID
- BINARY, CONVERT en consultas
- Backtick-quoted identifiers
- Triggers, stored procedures, functions, events
- Índices FULLTEXT
- Uploads locales
- Morph relations

## 3. Inventario de SQL Específico de MySQL

### Único hallazgo crítico

**Archivo**: `app/Modules/Reporting/Services/DashboardQueryService.php:244-263`
**Método**: `getDateExpression(string $groupBy): string`
**Problema**: El else asume MySQL cuando el driver no es sqlite.

```php
// Actual (líneas 246-263)
$driver = DB::getDriverName();
if ($driver === 'sqlite') {
    return match ($groupBy) {
        'day' => "strftime('%Y-%m-%d', o.effective_at)",
        'week' => "strftime('%Y-%u', o.effective_at)",
        'month' => "strftime('%Y-%m', o.effective_at)",
    };
}
// else: MySQL
return match ($groupBy) {
    'day' => "DATE(o.effective_at)",
    'week' => "DATE_FORMAT(o.effective_at, '%Y-%u')",
    'month' => "DATE_FORMAT(o.effective_at, '%Y-%m')",
};
```

**Corrección**: Agregar branch `pgsql` con `TO_CHAR()`.

### Consultas raw revisadas y compatibles

Todas las consultas `selectRaw()`, `orderByRaw()`, y `DB::raw()` en:
- DashboardQueryService (13 métodos)
- CalculateClosing
- DailyClosingController
- OperationController

Usan exclusivamente funciones ANSI SQL (COALESCE, SUM, COUNT, CASE WHEN, ABS). **Sin cambios
requeridos** salvo el branch de fechas documentado arriba.

### Transacciones y locks

`DB::transaction()` se usa en 15 ubicaciones. `lockForUpdate()` en 12 ubicaciones. Ambos son
portables entre MySQL y PostgreSQL. Verificar comportamiento con savepoints anidados en
PostgreSQL durante pruebas.

## 5. Decisiones de Arquitectura

### Decisión 1: Estrategia de migración

**Decisión**: Estrategia A — Migraciones Laravel + seeders controlados.

**Rationale**: Datos 100% dummy. La ruta `migrate:fresh --seed` crea el esquema completo desde
cero en PostgreSQL y puebla con datos de desarrollo controlados. No requiere transferencia de
datos, ETL, reconciliación ni sincronización de secuencias. El orden de carga lo determina
Laravel mediante dependencias de migración.

**Alternativas consideradas**:
- pgloader: Excesivo para datos dummy; añade dependencia externa sin beneficio.
- ETL con comando Artisan: Complejidad innecesaria sin datos reales que transferir.
- dump MySQL → psql: Incompatible sintácticamente; prohibido por spec.

### Decisión 2: Método de conexión Supabase

**Decisión**: Session Pooler (puerto 5432) como opción predeterminada.

**Rationale**: Render Free puede no garantizar conectividad IPv6 directa hacia Supabase. El Session
Pooler funciona sobre IPv4 y está diseñado para backends serverless/efímeros como Render. Soporta
prepared statements y transacciones (a diferencia del Transaction Pooler en puerto 6543). Se
probará conectividad real desde Render antes del despliegue definitivo.

**Alternativas consideradas**:
- Conexión directa IPv6: Preferible si está disponible (menos latencia, sin límite de prepared
  statements), pero Render Free puede no soportarla.
- Transaction Pooler: Incompatible con prepared statements y transacciones de Laravel por defecto.
  Solo se consideraría si se deshabilitan prepared statements y se prueban exhaustivamente locks,
  transacciones y migraciones.

### Decisión 3: Esquema PostgreSQL

**Decisión**: Esquema `public` (por defecto).

**Rationale**: Simplicidad para el MVP. Laravel configura `search_path=public` por defecto.
Migraciones y modelos no referencian esquemas explícitos. Si en el futuro se necesita aislar
tablas de aplicación de extensiones de Supabase, se migrará a un esquema dedicado.

### Decisión 4: Roles PostgreSQL

**Decisión**: Un solo rol con privilegios completos sobre el esquema `public` para el entorno
demo. Separación conceptual documentada para producción futura.

**Rationale**: Con Render Free + datos dummy, la complejidad de gestionar roles separados
(migración vs aplicación) no se justifica. El plan documenta la separación conceptual requerida
por spec (BR-013) para cuando se migre a plan pago con datos reales. En ese momento se crearán:
- `migration_role`: CREATE, ALTER, INDEX, migrations (solo durante deploys)
- `app_role`: SELECT, INSERT, UPDATE, DELETE sobre tablas de aplicación

### Decisión 5: Data API

**Decisión**: Deshabilitar completamente.

**Rationale**: La aplicación no tiene frontend que consuma Supabase directamente. Toda la lógica
pasa por Laravel. Deshabilitar Data API elimina la superficie de ataque REST/GraphQL sin requerir
configuración de RLS, esquemas separados ni políticas de seguridad.

### Decisión 6: Backups

**Decisión**: pg_dump lógico periódico + backups administrados de Supabase.

**Rationale**: Supabase Free incluye backups diarios automáticos. Adicionalmente, se ejecutará
`pg_dump --format=custom` antes y después de cada cambio de esquema significativo, almacenando
el dump fuera del filesystem de Render (descarga local o almacenamiento externo). La retención
y frecuencia se ajustarán al migrar a plan pago.

### Decisión 7: Rollback

**Decisión**: Rollback mediante backup del dump + migraciones revertidas.

**Rationale**: Como no hay datos reales que preservar, el rollback consiste en:
1. Restaurar dump de PostgreSQL previo al cambio
2. Revertir migraciones si es necesario
3. Re-desplegar versión anterior de la aplicación en Render
4. Apuntar conexión a MySQL si el rollback es total

El runbook de rollback incluye criterios de activación, responsable, tiempo máximo y comunicación.

### Decisión 8: Stack Docker para Render

**Decisión**: Nginx + PHP-FPM en imagen multi-stage.

**Rationale**: Render requiere un servidor HTTP que escuche en `$PORT`. Nginx como proxy reverso
hacia PHP-FPM es el stack más documentado para Laravel en Render. La imagen multi-stage separa
build (composer, npm, vite) de runtime (PHP-FPM, Nginx), minimizando el tamaño final.

**Alternativas consideradas**:
- FrankenPHP: Moderno (PHP + servidor HTTP en un binario), pero menos documentado en Render y
  requiere validación adicional de compatibilidad con extensiones.
- Apache + mod_php: Más pesado, menos eficiente en recursos limitados de Render Free.

### Decisión 9: Drivers de sesión y caché

**Decisión**: `database` para sesión y caché, `sync` para cola.

**Rationale**: Render tiene filesystem efímero. Los drivers `file` no sobreviven reinicios ni
arranques en frío. `database` usa PostgreSQL sin dependencias adicionales. `sync` para cola es
adecuado para un MVP sin procesos asíncronos.

### Decisión 10: Proceso de release

**Decisión**: Despliegue único con lock de migraciones.

**Rationale**: Render Free es single-instance. El entrypoint del Dockerfile ejecutará migraciones
con un lock basado en base de datos (`php artisan migrate --force --isolated`) para prevenir
ejecución concurrente si alguna vez se escala. Tras migraciones exitosas, inicia PHP-FPM y Nginx.

### Decisión 11: Configuración de logs

**Decisión**: Logs a stdout/stderr, nivel `error` en producción.

**Rationale**: Render captura automáticamente stdout/stderr y los expone en el dashboard. El
canal `stderr` para errores críticos y `stdout` para acceso. Sin archivos de log locales (efímeros).
LogSanitizer existente se aplica antes de emitir.

### Decisión 12: Observabilidad

**Decisión**: Health checks de liveness (`/up`) y readiness (`/health` con verificación PostgreSQL).

**Rationale**: Render usa HTTP health checks para determinar disponibilidad. `/up` (liveness)
verifica que la aplicación responde. `/health` (readiness) verifica conectividad a PostgreSQL
sin modificar datos ni exponer información interna. Render Free suspende el servicio tras
inactividad; el health check que verifica PostgreSQL permite distinguir "aplicación OK, DB
inaccesible" de "aplicación caída".
