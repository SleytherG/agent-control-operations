# Bug Assessment: cache_locks Table Missing on PostgreSQL

- **Slug**: cache-locks-table-missing
- **Created**: 2026-07-25
- **Source**: pasted text (Render deployment logs)
- **Verdict**: valid
- **Severity**: critical

## Report (verbatim)

```
SQLSTATE[42P01]: Undefined table: 7 ERROR:  relation "cache_locks" does not exist
LINE 1: update "cache_locks" set "owner" = $1, "expiration" = $2 whe...
                 ^
```

Stack trace: `CacheCommandMutex::create()` → `DatabaseLock::acquire()` → query on `cache_locks`
→ PDOException. This happens during `php artisan migrate --force --isolated` in the entrypoint.

## Symptom

The Render entrypoint (`docker/entrypoint.sh`) runs `php artisan migrate --force --isolated`.
The `--isolated` flag uses `CacheCommandMutex` which requires a `cache_locks` table for the
`database` cache driver. Since `CACHE_STORE=database` but the cache tables migration was
never created, the mutex fails with "relation 'cache_locks' does not exist". The deploy
never completes.

## Reproduction

1. Set `CACHE_STORE=database` and `DB_CONNECTION=pgsql`
2. Run `php artisan migrate --force --isolated` on a fresh PostgreSQL database
3. Observe `SQLSTATE[42P01]: relation "cache_locks" does not exist`

## Suspected Code Paths

- `docker/entrypoint.sh:5` — `php artisan migrate --force --isolated` triggers the cache mutex
- `vendor/laravel/framework/src/Illuminate/Console/CacheCommandMutex.php:57` — tries to acquire a cache lock on the `cache_locks` table
- `vendor/laravel/framework/src/Illuminate/Cache/DatabaseLock.php:85` — queries `cache_locks`

## Root Cause Hypothesis

**Confidence: high.**

The project uses `CACHE_STORE=database` but never ran `php artisan cache:table` to generate
the migration that creates the `cache` and `cache_locks` tables. The `--isolated` flag on
`php artisan migrate` requires a working cache mutex, which requires the cache tables to
exist. Without them, no Artisan command using `--isolated` can run.

## Proposed Remediation

**Preferred**: Generate and run the cache tables migration:

```bash
php artisan cache:table
```

Then commit the generated migration file. On Render, the entrypoint already runs
`php artisan migrate` which will create the cache tables on first deploy. But this
creates a chicken-and-egg problem: the very first `migrate --isolated` needs the tables
to exist, but the migration that creates them hasn't run yet.

**Fix**: Remove `--isolated` from the entrypoint for the first deploy (or use Redis/file
cache for the mutex). Alternative: split the entrypoint to run migrations without `--isolated`
first (to create cache tables), then subsequent commands can use it.

Simpler fix: change the entrypoint to run `php artisan migrate --force` (without `--isolated`)
which doesn't use the cache mutex. On a single-instance Render Free plan, there's no risk of
concurrent migration execution.

**Files likely to change**:
- `docker/entrypoint.sh` — remove `--isolated` flag
- New migration file generated by `php artisan cache:table`

**Tests to add or update**:
- Smoke test: verify `php artisan migrate --force` succeeds on fresh PostgreSQL after
  cache table migration is in place

## Risks & Considerations

- Removing `--isolated` is safe on single-instance deployments. If scaling to multiple
  instances later, re-add `--isolated` (by then the cache tables will already exist).
- The cache tables migration must be committed so future deploys include it.
