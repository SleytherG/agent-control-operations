# Bug Assessment: Mixed content — assets loaded over HTTP on HTTPS page

- **Slug**: mixed-content-https
- **Created**: 2026-07-27
- **Source**: pasted text
- **Verdict**: valid
- **Severity**: high

## Report (verbatim or summarized)

> "Veo que al entrar a la ruta https://agent-control-operations.onrender.com/login, pero todos los estilos no cargan... y en la consola sale esto Mixed Content: The page at 'https://agent-control-operations.onrender.com/login' was loaded over HTTPS, but requested an insecure stylesheet 'http://agent-control-operations.onrender.com/build/assets/app-ZnPhLBlN.css'."

Browser console errors:
```
Mixed Content: The page at 'https://agent-control-operations.onrender.com/login' was loaded over HTTPS, but requested an insecure stylesheet 'http://agent-control-operations.onrender.com/build/assets/app-ZnPhLBlN.css'. This request has been blocked; the content must be served over HTTPS.
Mixed Content: The page at 'https://agent-control-operations.onrender.com/login' was loaded over HTTPS, but requested an insecure script 'http://agent-control-operations.onrender.com/build/assets/app-orPx7SgZ.js'.
Mixed Content: The page at 'https://agent-control-operations.onrender.com/login' was loaded over HTTPS, but requested an insecure script 'http://agent-control-operations.onrender.com/build/assets/session-timer-QPYjZFYb.js'.
```

Additionally, the login form itself targets `http://agent-control-operations.onrender.com/login` instead of `https://`.

## Symptom

All CSS, JS, and form actions on the page use `http://` URLs instead of `https://`, causing browsers to block assets as Mixed Content. The page renders without styles and without JavaScript functionality (login won't work, session timer won't run). The expected behavior is that all asset URLs and form actions use `https://` to match the page protocol.

## Reproduction

1. Visit `https://agent-control-operations.onrender.com/login` in any modern browser.
2. Open DevTools → Console.
3. Observe multiple "Mixed Content" errors for CSS and JS assets.
4. Observe the page renders without styles (no CSS applied, layout broken).

## Suspected Code Paths

- `bootstrap/app.php:17-28` — `->withMiddleware()` does not call `$middleware->trustProxies()`. The `TRUSTED_PROXIES` env var (`*` in `render.yaml:46`) is set but never consumed. Laravel's `TrustProxies` middleware is in the global stack but with a null `$proxies` property, so it never trusts Render's proxy IPs.
- `docker/nginx.conf:26-31` — the `location ~ \.php$` block does not forward `X-Forwarded-Proto`, `X-Forwarded-For`, `X-Forwarded-Host`, or `X-Forwarded-Port` headers to PHP-FPM. Render terminates TLS at its edge proxy and sends `X-Forwarded-Proto: https`, but Nginx discards it before it reaches Laravel.
- `render.yaml:15-19` — `APP_URL` is resolved via `fromService` → `property: host`, which returns just the bare hostname (e.g., `agent-control-operations.onrender.com`) without the `https://` scheme.
- `config/app.php:55` — `APP_URL` defaults to `'http://localhost'` when the env var is missing or malformed.
- `resources/views/layouts/guest.blade.php:8-9` and `resources/views/layouts/authenticated.blade.php:11-12` — `@vite()` directives generate `<link>` and `<script>` tags whose URLs depend on `APP_URL` / `asset()` helper, which resolves to `http://` when the scheme is unknown.

## Root Cause Hypothesis

**Confidence: high.** Render terminates TLS at its edge proxy and forwards requests to the container over plain HTTP with `X-Forwarded-Proto: https`. The application has three missing pieces that prevent it from detecting HTTPS:

1. **Nginx does not forward the `X-Forwarded-*` headers to PHP-FPM** — so `$_SERVER['HTTP_X_FORWARDED_PROTO']` is never set.
2. **Laravel's `TrustProxies` middleware is not configured** — even if the headers reached PHP, the app wouldn't trust them because no proxy IPs are configured.
3. **`APP_URL` lacks the `https://` scheme** — Render's `fromService` returns a bare hostname, so the fallback chain ends at `http://localhost`.

Result: Laravel's `Request::isSecure()` returns `false`, `URL::forceScheme()` is never called, and all asset URLs generated by `@vite()` / `asset()` use `http://`.

## Proposed Remediation

**Preferred** (three changes, all required):

1. **`bootstrap/app.php`** — add `$middleware->trustProxies(at: env('TRUSTED_PROXIES', null))` inside `withMiddleware()`. This tells Laravel to trust the `X-Forwarded-*` headers from proxy IPs matching the pattern (already set to `*` in `render.yaml`).

2. **`docker/nginx.conf`** — add explicit `fastcgi_param` directives in the `location ~ \.php$` block to forward `X-Forwarded-Proto`, `X-Forwarded-For`, `X-Forwarded-Host`, and `X-Forwarded-Port` from Nginx's `$http_*` variables to PHP-FPM's `$_SERVER` superglobal. Without this, step 1 has no headers to trust.

3. **`render.yaml`** — set `APP_URL` explicitly to `https://agent-control-operations.onrender.com` (or keep `fromService` but ensure the scheme is prepended). Since `fromService` only returns a hostname, hardcoding the value with the `https://` prefix is the most reliable approach for the free Render plan (single service, fixed hostname).

**Alternatives**:
- Skip steps 1–2 and only fix `APP_URL` in `render.yaml`. This fixes asset URLs but not form actions (`url()->current()`, `route()`, etc.) and breaks secure cookie validation (`__Host-` prefix requires HTTPS).
- Add `URL::forceScheme('https')` in `AppServiceProvider::boot()` when `APP_ENV=production`. This is a blunt instrument that forces all URL generation to HTTPS regardless of proxy headers; it works but is less correct than trusting proxy headers.

**Files likely to change**:
- `bootstrap/app.php`
- `docker/nginx.conf`
- `render.yaml`

**Tests to add or update**:
- Integration test: verify `Request::isSecure()` returns true when `X-Forwarded-Proto: https` is present (after proxy trust config).
- Smoke test: after redeploy, verify all `<link>` and `<script>` tags use `https://` URLs.

## Risks & Considerations

- Using `*` for trusted proxies is acceptable on Render's free tier (single container, no shared network) but would be a security concern in multi-tenant environments. The app already sets `TRUSTED_PROXIES: "*"` in `render.yaml`.
- The Nginx config change is additive (adds `fastcgi_param` lines); it does not modify existing behavior.
- Hardcoding `APP_URL` in `render.yaml` means the URL must be updated if the Render service name changes.
- The `__Host-` cookie prefix requires HTTPS. If the app can't detect HTTPS, cookies using this prefix will be rejected by browsers, breaking authentication entirely.
