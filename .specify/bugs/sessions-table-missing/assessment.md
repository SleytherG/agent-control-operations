# Bug Assessment: Missing sessions table causes 500 on all routes

- **Created**: 2026-07-26

- **Verdict**: valid
- **Severity**: critical

## Symptom

Every HTTP request — including `/login` (a guest route) — returns HTTP 500. Laravel's `StartSession` middleware initializes the session via the `database` driver, which queries the `sessions` table. That table does not exist because no migration was ever generated for it, causing `DatabaseSessionHandler::read()` to throw a fatal database error.

## Reproduction

1. Deploy to Render with `SESSION_DRIVER=database` (as configured in `render.yaml`).
2. Visit `https://agent-control-operations.onrender.com/login`.
3. Observe HTTP 500.

## Suspected Code Paths

- `Illuminate\Session\Middleware\StartSession` (Laravel framework) — runs on every request via `web` middleware group; calls `Store::start()` → `Store::loadSession()` → `Store::readFromHandler()`.
- `Illuminate\Session\DatabaseSessionHandler::read()` (Laravel framework) — attempts `find()` on the `sessions` table; the table does not exist.
- `render.yaml:37-38` — `SESSION_DRIVER: database` enforces the database driver in production.
- `database/migrations/` — no migration exists for the `sessions` table (only custom `auth_sessions`, `session_events`, `cache`, `cache_locks` tables exist).

## Root Cause Hypothesis

**Confidence: high.** The application is configured to use `SESSION_DRIVER=database` (both in `.env` and `render.yaml`), but the `sessions` table was never created because no migration for it exists. The `php artisan migrate --force` command in `docker/entrypoint.sh:8` runs all available migrations, but since none of them create the `sessions` table, the table is absent in production.

The `auth_sessions` table (created by `2026_07_22_000003_create_auth_sessions_table.php`) is a custom table for JWT-based authentication sessions — it is **not** the Laravel-native sessions table required by the `database` session driver.

## Proposed Remediation

**Preferred**: Generate the Laravel sessions table migration via `php artisan session:table` and commit it. The migration creates the `sessions` table with the schema expected by `DatabaseSessionHandler` (`id`, `user_id`, `ip_address`, `user_agent`, `payload`, `last_activity`). Since `docker/entrypoint.sh` already runs `php artisan migrate --force` on deploy, the table will be created automatically on the next deployment.

**Alternatives**:
- Change `SESSION_DRIVER` to `cookie` — stores session data in encrypted cookies, no database table needed. Works well with Render's ephemeral filesystem and eliminates the database dependency for session storage. However, this changes the session architecture and may have implications if any shared session behavior is expected.
- Change `SESSION_DRIVER` to `file` — stores sessions on disk. Works but sessions are lost on every Render redeploy (ephemeral storage), and Render's filesystem is not shared across instances.

**Files likely to change**:
- `database/migrations/<timestamp>_create_sessions_table.php` (new file — generated by `php artisan session:table`)

**Tests to add or update**:
- Smoke test: deploy and verify that `/login`, `/up`, and `/health` all return non-500 status codes.
- Integration test: verify that CSRF token generation and validation work correctly, since CSRF relies on session storage.

## Risks & Considerations

- The `sessions` table will grow unboundedly unless garbage collection is configured. Laravel's session GC runs on a lottery basis (`session.lottery`) and removes expired sessions. Verify this is not disabled in production.
- If the PostgreSQL connection fails or the database is not reachable, the same 500 error will still occur. The database connectivity itself should be verified independently.
- The app uses JWT tokens for authentication (stored in `__Host-access_token` / `__Host-refresh_token` cookies), so the `sessions` table is only used for Laravel's native session features: CSRF tokens, flash messages, and `session()` helper storage.
